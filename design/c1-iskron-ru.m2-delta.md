Новый носитель поверхности: `.c1-inputs/m2-surface-ru-iskron.json`, sha256 `6ae80bd08a826d088b1333dbd8203ed35d01d7fff01e8074a2118c7d828b9ce4` — хеш проверен. Прежний носитель M1: `server-export-ru-iskron.json`, `71d15ede…`.

Сам проект, C1 и черновики не меняются. Узлы графа не читались.

**Что сверено.** Я сравнил M1 и M2 по каждому тулу (структурный JSON-дифф). Расхождения — ровно 15 описаний: в 9 тулах (`add_*` ×6, `arrow`, `update`, `batch`) «≤99999 знаков» заменено на «≤64 знаков». Кроме того, в M2 появился корневой ключ `attrsLimit: 64`. Остальное совпало: справки `help` побайтно, набор из 21 тула, все прочие описания и схемы.

**Оговорка о номерах строк.** Физические номера строк в M2 сдвинуты, потому что файл иначе отформатирован. Ссылки проекта `S:N` поэтому адресуют файл M1. Цитаты, на которые они опираются, в M2 побайтно те же (дифф затрагивает только описания attrs), так что адресация по имени тула и параметра остаётся верной.

**Граница 64 и область усмотрения.** Там, где проект говорит об attrs, он говорит о *роде* содержимого: ключи фильтра, а не проза; не глушить натяжения. О длине он не говорит ничего. Число 64 — предел контура, его держит сервер. Навык его не дублирует, и проекту дублировать не нужно: `writing:88` уже ссылается на отказ поверхности, а не называет число. Добавлять число в навык не предлагаю, иначе появится второй носитель предела, который расходится молча. Усмотрение агента остаётся прежним: что класть в attrs как ключ, решает он; длину решает контур.

## 2. Способ счёта бюджета (№651 [36]) и §9 проекта

**Предел проекта сужен, но не закрыт.** Раньше было «способ счёта не найден» (§9, §14). Теперь способ назван: `npm run cost` в nks-mcp. Строка каталога — «<сигнатура Code Mode> // <первая строка описания ≤120>»; токены = знаки/4 (оценка); предел 9500; описания параметров входят в сигнатуру; справки в каталог не входят; ограничения tools/list ≤125000 знаков, одно описание ≤10000, док аргумента ≤520.

Я сам `npm run cost` не запускал: репозиторий nks-mcp чужой и вне моего мандата. Поэтому всё ниже — оценки по M2, а не измерения.

**Что это меняет в §9:**

1. **Какие пункты M нагружают каталог.** Только правки *описаний параметров*: M3 (`update.volitive_mode`) и M4 (`epistemic_mode`). Правки тела описания (M1, M2, M5, M7a, M7b) каталог не задевают — первая строка у них не меняется. Они нагружают только tools/list и предел одного описания. Справки (M6, M8, M9, M10) не нагружают ни то, ни другое. Это подтверждает исправление E3 круга 1 и сужает его: описания параметров учитываются точно.
2. **Оценки по M2** (знаки/4):
   - M3: 99 → ≈130 знаков → **≈+8 ток.**
   - M4 *заменой* трёх параметров (160, 132, 156 → ≈145 каждый): ≈−15…+15 знаков → **≈0 ток.**
   - M4 *добавкой* к нынешним текстам: ≈+435 знаков → **≈+110 ток.**
   - Хвост M4 «так же в inline-модусах других фабрик», если он означает *новые* описания у `arrows[].epistemic_mode` семи тулов: до ≈+1000 знаков → **≈+250 ток.** Это больше остатка 9500 − 9252 = 248.

   Вывод: M4 исполнимо только как замена. Inline-хвост — заменой там, где описание уже есть, а новых описаний не заводить. Это уточнение исполнения, а не смены смысла.
3. **Резерв от строки моста (Р1) — не резерв каталога.** Мостовой префикс стоит первой строкой описания семи пишущих тулов. Каталог берёт первую строку, обрезанную до 120 знаков, — и прежняя, и короткая строка Р1 займут свои 120 знаков. Значит, Р1 каталог почти не меняет: сервер префикса не видит, после моста строка всё равно режется до 120.

   Р1 разгружает только *tools/list после моста*. По моей мере (компактный JSON массива tools) это 126 221 знак для postbridge M1 при пределе 125 000. M2 серверный — 118 849. Совпадает ли моя мера с мерой `npm run cost` и относится ли предел 125 000 к выдаче после моста — источник не говорит. Если относится, короткая строка Р1 (≈−400 знаков × 7) из выбора бюджета становится нужной.

   Фразу §9 «укорочение семи префиксов — кандидат в резерв» следует читать как резерв tools/list, а не каталога 9500.
4. **Грубая самопроверка меры.** Моя приблизительная сумма по M2 (имя, параметры с описаниями и enum, первая строка ≤120) — ≈35 600 знаков ≈ 8 900 ток. Названное #163 значение ≈9252 того же порядка. Расхождение ожидаемо: точный рендер сигнатуры Code Mode и вложенные `arrows` я не воспроизводил. Это проверка порядка величины, а не измерение.
5. **Пределы аргумента и описания.** Предложенные тексты M3/M4 — до ≈150 знаков, меньше 520. Самое длинное описание после M1/M7b — `add_vimarsha` (9 060; проектом не трогается) и `add_kriya` (≈6 040 + ≈100), меньше 10 000. После моста `add_vimarsha` = 9 060 + префикс 630 = 9 690, это ещё укладывается в 10 000, но запас мал. Входит ли мостовой префикс в предел одного описания — источник не говорит.
6. **Попутное наблюдение для #931, вне C1.** В каталоге после моста первой строкой семи пишущих тулов стоит строка моста, а не назначение тула: так это видно в каталоге Code Mode этой сессии (`iskron_add_bianhua` → «[мост] Момент скилла writing: …»). Р1 этого не меняет. Если назначение тула в каталоге важно для распознавания, это отдельный вопрос к мосту, а не к C1.

**Гейт §9 не меняется:** head ≤ base и ≤ 9500 тем же прибором (`npm run cost`), плюс отдельный замер выдачи после моста.
