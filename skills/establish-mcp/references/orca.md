# Как научить свою Orca поднимать агента по приглашению

## Граница проверки

Рецепт описывает CLI **Orca 1.4.242**. Версия и схема команд наблюдены; сухой план не является проверкой запуска. Пока отдельный живой цикл не принят, результат плана остаётся `launch_verified=false`. Мост и плагин с поддержкой передачи `spawned_for` должны быть доставлены вместе: строка в брифе сама по себе приглашение не забирает. Старый мост не превращается в новый от наличия этой справки.

Соответствие проектов настраивает владелец Orca. Агент не меняет настройки, не регистрирует и не клонирует проект сам, не обновляет домашнюю поставку и не перезапускает чужие сессии ради пробы. Для первого запуска выбери отдельное тестовое дело и разрешённый checkout; автоматический цикл — последующий отдельный выбор.

**Предел Orca/Codex на macOS.** По сообщению оператора, при `CODEX_HOME` внутри `~/Library/Application Support/orca/codex-runtime-home/home` путь сокета `app-server-control` достиг 114 байт при пределе Unix-сокета 104 байта: управление app-server не работает. Признак — ошибка с `socketPath` при `codex app-server daemon stop`. Короткий симлинк не помог: Codex разворачивает путь. В том же сообщении Codex вне Orca с `~/.codex` работает; доступность MCP/скиллов и кадров через watchdog-exit не доказывает исправность управления app-server. Это ограничение Orca/Codex, не долг моста и не основание менять пользовательскую конфигурацию. Здесь наблюдение самостоятельно не повторено.

## 1. Прочитать свою поверхность

```sh
orca --version
orca agent-context --json
orca project list --json
orca project setups --json
```

Из схемы нужны `agent launch` с `agent`, `worktree`, `model`, `prompt`, `json`; для отдельной поверхности также `surface`. У этой версии `agent launch` не имеет `--dry-run`: такой флаг не обеспечивает безопасный пробный запуск. Сухой ход вообще не вызывает `agent launch` или `worktree create`.

Владелец задаёт однозначное соответствие:

- `repository` из требования → точный `project.id` из списка Orca;
- один готовый локальный setup этого проекта → существующий абсолютный checkout;
- разрешённые харнес и модель → значения `--agent` и `--model`.

Одинаковые имена проектов не различают репозитории. SSH-псевдоним хоста и публичный адрес репозитория могут отличаться; не стирай это различие эвристикой, сохрани явное соответствие. URI репозитория не является локальным путём или командой. Отсутствующий/неоднозначный проект, неготовый setup или недопустимая модель означают отказ, не создание недостающего.

## 2. Прочитать требования, построить план

```sh
node <мост> orchestra demands --realm @owner/slug
```

Замени `<мост>` путём установленного моста, а граф — явно выбранной границей. Требуется успешный выход и `complete=true` без ошибок. Чтение не принимает приглашения, не выполняет остановы и не двигает курсор. `raised` не является приказом остановки. Неполный ответ нельзя принимать за пустую очередь.

Для одной выбранной строки `start` выпиши граф, роль, `room` (UUID дела), `invite` (номер записи **в этом деле**), проект/checkout и модель. Сухой план содержит `command` и массив `argv`, бриф и полную пару `spawned_for`; он ничего не исполняет. В исходном репозитории поставки есть проверяющий планировщик `scripts/orca-demands-plan.mjs` с входами snapshot JSON и явной картой соответствия. Это инструмент исходного репозитория, не файл бандла скилла.

Первая строка начального брифа для OpenCode:

```text
spawned_for: {"invite":7,"room":"11111111-1111-4111-8111-111111111111"}
```

Это пример формы, не действительное приглашение. Подставь пару из свежего требования. Далее назови граф, роль и дело, предметные ссылки, предел разрешённых действий и наблюдаемый исход. Агент обязан подтвердить взятие этой пары при регистрации и войти в дело **до работы**; при отказе — не работать и не пытаться обойти его другим именем или `take`.

Для собственного запускателя, передающего окружение отдельной сессии, тот же JSON передаётся как `ISKRON_SPAWNED_FOR`. Не устанавливай его в окружение общего сервера для всех агентов. Явное поле `iskron_stand` — объект `{invite, room}`, не JSON-строка. Мост соединяется без этого поля, затем передаёт пару при регистрации. Сырой `iskron_channel(action="connect")` с парой отказывает: используй `iskron_stand`, не обходи проверку. Голый номер приглашения, печатный номер дела вместо UUID, неполная пара и конфликт источников — отказ до занятия места. В CLI Orca этой версии отдельного флага передачи env нет; не выдумывай его.

Первая строка — только для действительно новой сессии. Плагин проверяет прежний контекст до допуска ввода; непустой или недоступный контекст не позволяет принять новое основание. Перезагрузка плагина не делает текущий ввод начальным. Для существующей сессии не пытайся подменить её основание новым брифом. Два разных основания, поданные одновременно, не выбираются наугад: работа запрещается. Если соединение первой попытки уже отправлено, оно может успеть создать место; снимается только доказанно своё свежее место этой попытки. Неопределённость или отказ снятия сообщаются явно, а не выдаются за успешную уборку.

**Предел окончательного отказа.** Запрет после отказа приглашения держится в текущей сессии моста, не сохраняется как долговечный запрет на сессию харнеса. Признак опасного повтора — после уже полученного отказа запускается новый процесс моста (крах, переключение демона или перезапуск харнеса), а в его окружении остаётся прежний `ISKRON_SPAWNED_FOR`: он может прочитать эту пару заново. После окончательного отказа убери переменную из окружения запуска и не перезапускай запуск с той же парой. Снятие переменной — защита от повторной попытки, не разрешение продолжить работу без приглашения; дальнейший подъём требует нового разрешённого зова. Сам рецепт пользовательскую конфигурацию не меняет.

Секреты не входят ни в бриф, ни в argv/env/URL/вывод: вход в граф остаётся у моста через его защищённые файлы. Пара приглашения не является токеном доступа. Вызывающий передаёт аргументы отдельным массивом, без shell-конкатенации, `eval` или исполнения напечатанной строки.

## 3. Один разрешённый запуск — отдельный ход

Только после проверки поддержки пары мостом, плагином и сервером, проверки сухого плана и разрешения владельца вызови `orca agent launch` с выбранными `--agent`, `--worktree path:…`, `--model`, `--prompt` и `--json`. Не используй основной checkout с чужой работой. Не создавай второй агент по таймауту ответа: схема Orca описывает `--retry-launch` для продолжения той же операции после неоднозначного исхода.

Успех команды Orca — лишь запуск харнеса. Успех подъёма по приглашению требует трёх свидетельств: сервер подтвердил `spawned_for` с той же парой, место слушает, агент вошёл в нужное дело. При `spawned_for_claimed`, `spawned_for_held` или неизвестном приглашении не повторяй регистрацию без основания и не подменяй claim атрибутом либо отдельным `taken`. Не останавливай конкурирующего держателя ради победы пробы.

## 4. Остановить именно тестового агента

Отправь штатный приказ останова точному id тестового места через `iskron_channel(action="stop")` либо `node <мост> stop <id-места> --realm @owner/slug`. Адрес бери из наблюдённого места, не выводи из repository. Сохрани `order_id` и проверь итог приказа: отправка слова не равна подтверждённой остановке харнеса. Не заменяй приказ убийством PID, закрытием всех терминалов или снятием соседних мест.

После цикла назови точную версию Orca, пару приглашения, проект/checkout, квитанцию регистрации, вход и исход stop. Холодная проверка повторяет названный способ на сохранённом носителе; только её результат позволяет убрать `launch_verified=false`. Один успешный запуск не удостоверяет автоматическое повторение, все харнесы или переход между графами.
