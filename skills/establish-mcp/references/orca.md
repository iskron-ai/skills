# Как научить свою Orca поднимать агента по приглашению

## Включить автоподъём без агента

Для человека, в своём терминале. Мост — `~/.iskron-bridge/iskron-bridge.mjs`; его демон уже жив, если открыта любая сессия харнеса с мостом. Нужны Orca с настроенным проектом репозитория и у предмета зова атрибут `repository`.

1. Посмотреть, что лежит: `node ~/.iskron-bridge/iskron-bridge.mjs orchestra status`.
2. Сухой такт — что поднялось бы сейчас, ничего не запуская и не спрашивая Orca:

   ```sh
   node ~/.iskron-bridge/iskron-bridge.mjs orchestra step --dry-run --realm @owner/slug
   ```

   По каждому зову — «поднял бы: orca agent launch …» или «отказал бы: код» (коды — раздел «Оркестратор моста» скилла **establish-mcp**). Копию, которую назовёт Orca, сухой такт показывает заглушкой. Граф — внутри границы машины: названный прежним `on` или граф агента, живого на ней сейчас; иначе отказ `outside_boundary`.
3. Включить — одна команда; набранная в терминале, она и есть согласие машины (переменная и перезапуск не нужны):

   ```sh
   node ~/.iskron-bridge/iskron-bridge.mjs orchestra on --realm @owner/slug \
     --launcher mac --model anthropic/claude-opus-5-5 --limit 2
   ```

   `--launcher` — имя запускателя до 64 знаков (длиннее — отказ): им роли будут звать агентов. Описания с этим именем в mind нет — команда его запишет под холоном работы с агентами (тем, что держит карточки `slice:agents`; не нашёлся один — в корень, и ответ это скажет) (`--model` — можно несколько, `--limit` — агентов разом, по умолчанию 1, `--host` — имя машины, без него отвечает любая машина учётки); есть — берётся как лежит, правится в mind. Без `--launcher` — только флаг и граница.
4. Проверить: `… orchestra status` — «включён» и граница; такт идёт сам раз в минуту, `… orchestra step` — сейчас.
5. Остановить одного агента — `node ~/.iskron-bridge/iskron-bridge.mjs stop <место> --realm @owner/slug`. Приказ сам по себе не доказывает выход клиента, закрытие вкладки или свободный слот. Различение прежних запусков и нового пути со своим деревом либо exec, условия завершения и коды неизвестного исхода — раздел «Оркестратор моста» в [SKILL.md](../SKILL.md); проверь наблюдённый исход по нему.
6. Выключить — `… orchestra off`: снимает флаг и согласие из терминала (согласие `ISKRON_ORCHESTRA=1` живёт, пока переменная в окружении демона); поднятые агенты доживают сами. Следующее включение — снова из терминала, если согласие давал терминал; при `ISKRON_ORCHESTRA=1` у демона оно проходит без терминала.

## Граница проверки

Это ручной путь: свой запускатель или разбор Orca по шагам. Автоматический — оркестратор моста (раздел «Оркестратор моста» скилла **establish-mcp**): он сам сверяет версию и схему Orca перед запуском. Сухой план не является проверкой запуска. Строка в брифе сама по себе приглашение не забирает: пару `spawned_for` принимает только мост, который её знает, — его поле называет описание тула `iskron_stand` в этой сессии. Поля нет — мост старый: скажи человеку, что нужен `update`, сам не обновляй.

Соответствие проектов настраивает владелец Orca. Агент не меняет настройки, не регистрирует и не клонирует проект сам, не обновляет домашнюю поставку и не перезапускает чужие сессии ради пробы. Для первого запуска выбери отдельное тестовое дело и разрешённую рабочую копию.

**Codex под Orca на macOS** может не управлять своим app-server (признак — ошибка с `socketPath` при `codex app-server daemon stop`): это предел Orca и Codex, не моста; конфигурацию человека ради него не меняй.

## 1. Прочитать свою поверхность

```sh
orca --version
orca agent-context --json
orca project list --json
orca project setups --json
```

Из схемы нужны `agent launch` с `agent`, `worktree`, `model`, `prompt`, `json`; для отдельной поверхности также `surface`. У этой версии `agent launch` не имеет `--dry-run`: такой флаг не обеспечивает безопасный пробный запуск. Сухой ход вообще не вызывает `agent launch` или `worktree create`.

Владелец задаёт однозначное соответствие:

- `repository` из требования → точный `project.id` из списка Orca;
- одна готовая локальная установка (setup) этого проекта → существующая рабочая копия по абсолютному пути;
- разрешённые харнес и модель → значения `--agent` и `--model`.

Одинаковые имена проектов не различают репозитории. SSH-псевдоним хоста и публичный адрес репозитория могут отличаться; не стирай это различие эвристикой, сохрани явное соответствие. URI репозитория не является локальным путём или командой. Отсутствующий/неоднозначный проект, неготовая установка или недопустимая модель означают отказ, не создание недостающего.

## 2. Прочитать требования, построить план

```sh
node <мост> orchestra demands --realm @owner/slug
```

Замени `<мост>` путём установленного моста, а граф — явно выбранной границей. Требуется успешный выход и `complete=true` без ошибок. Чтение не принимает приглашения, не выполняет остановы и не двигает курсор. `raised` не является приказом остановки. Неполный ответ нельзя принимать за пустую очередь.

Для одной выбранной строки `start` выпиши граф, роль, `room` (UUID дела), `invite` (номер записи **в этом деле**), проект/checkout и модель. Сухой план содержит `command` и массив `argv`, бриф и полную пару `spawned_for`; он ничего не исполняет.

Начальный бриф для OpenCode — одна строка: пара, пробел, бриф.

```text
spawned_for: {"invite":7,"room":"11111111-1111-4111-8111-111111111111"} Войди в дело …
```

Это пример формы, не действительное приглашение. Подставь пару из свежего требования. Многострочный `--prompt` терминал OpenCode кладёт вставкой в поле ввода и не отправляет; пара отдельной первой строкой допустима только там, где ввод отправляется целиком. После пары назови граф, роль и дело, предметные ссылки, предел разрешённых действий и наблюдаемый исход. Агент обязан подтвердить взятие этой пары при регистрации и войти в дело **до работы**; при отказе — не работать и не пытаться обойти его другим именем или `take`.

Для собственного запускателя, передающего окружение отдельной сессии, тот же JSON передаётся как `ISKRON_SPAWNED_FOR`. Не устанавливай его в окружение общего сервера для всех агентов. Явная передача — полем `iskron_stand` по его описанию; сырой `iskron_channel(action="connect")` с парой отказывает — не обходи проверку. Голый номер приглашения, печатный номер дела вместо UUID, неполная пара и конфликт источников — отказ до занятия места. В CLI Orca этой версии отдельного флага передачи env нет; не выдумывай его.

Первая строка — только для действительно новой сессии. Плагин проверяет прежний контекст до допуска ввода; непустой или недоступный контекст не позволяет принять новое основание. Перезагрузка плагина не делает текущий ввод начальным. Для существующей сессии не пытайся подменить её основание новым брифом. Два разных основания, поданные одновременно, не выбираются наугад: работа запрещается. Если соединение первой попытки уже отправлено, оно может успеть создать место; снимается только доказанно своё свежее место этой попытки. Неопределённость или отказ снятия сообщаются явно, а не выдаются за успешную уборку.

**Предел окончательного отказа.** Запрет после отказа приглашения держится в текущей сессии моста, не сохраняется как долговечный запрет на сессию харнеса. Признак опасного повтора — после уже полученного отказа запускается новый процесс моста (крах, переключение демона или перезапуск харнеса), а в его окружении остаётся прежний `ISKRON_SPAWNED_FOR`: он может прочитать эту пару заново. После окончательного отказа убери переменную из окружения запуска и не перезапускай запуск с той же парой. Снятие переменной — защита от повторной попытки, не разрешение продолжить работу без приглашения; дальнейший подъём требует нового разрешённого зова. Сам рецепт пользовательскую конфигурацию не меняет.

Секреты не входят ни в бриф, ни в argv/env/URL/вывод: вход в граф остаётся у моста через его защищённые файлы. Пара приглашения не является токеном доступа. Вызывающий передаёт аргументы отдельным массивом, без shell-конкатенации, `eval` или исполнения напечатанной строки.

## 3. Один разрешённый запуск — отдельный ход

Только после проверки поддержки пары (поле `spawned_for` в описании `iskron_stand`, раздел «Граница проверки»), проверки сухого плана и разрешения владельца вызови `orca agent launch` с выбранными `--agent`, `--worktree path:…`, `--model`, `--prompt` и `--json`. Не используй основной checkout с чужой работой. Не создавай второй агент по таймауту ответа: схема Orca описывает `--retry-launch` для продолжения той же операции после неоднозначного исхода.

Успех команды Orca — лишь запуск харнеса. Успех подъёма по приглашению требует трёх свидетельств: сервер подтвердил `spawned_for` с той же парой, место слушает, агент вошёл в нужное дело. При `spawned_for_claimed`, `spawned_for_held` или неизвестном приглашении не повторяй регистрацию без основания и не подменяй claim атрибутом либо отдельным `taken`. Не останавливай конкурирующего держателя ради победы пробы.

## 4. Остановить именно тестового агента

Отправь штатный приказ останова точному id тестового места через `iskron_channel(action="stop")` либо `node <мост> stop <id-места> --realm @owner/slug`. Адрес бери из наблюдённого места, не выводи из repository. Сохрани `order_id` и проверь итог приказа: отправка слова не равна подтверждённой остановке харнеса. Не заменяй приказ убийством PID, закрытием всех терминалов или снятием соседних мест.

После цикла назови точную версию Orca, пару приглашения, проект/checkout, квитанцию регистрации, вход и исход stop. Холодная проверка повторяет названный способ на сохранённом носителе; только её результат считается проверкой запуска. Один успешный запуск не удостоверяет автоматическое повторение, все харнесы или переход между графами.
