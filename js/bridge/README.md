# js/bridge — ядро MCP-моста

Вход процесса — `main.ts`, цикл — `engine.ts` и `deliver.ts`; демон машины и тонкий клиент — `daemon.ts` и `thin.ts`.

- `spawned-for.ts` — основание запуска по #9959: явная пара либо окружение области сессии, закреплённое за одним графом и ролью; на MCP-проводе поле получает только register. `claimdelivery.ts` проверяет вход и ответ register до привязки; `claimseat.ts` держит независимую идентичность своего connect/held для выбора квитанции. `call.ts` и `standing.ts` используют ту же проверку внутренних регистраций; `standanswer.ts` — итог stand с выбранной seats-квитанцией и признаком свежести этой попытки. `standcwd.ts` — проверка каталога для stand и его занятости. `standundo.ts` снимает только своё новое место после отказа регистрации. Нижние пробы — `stand.test.mjs`, `daemon.test.mjs`; реальную Orca не удостоверяют.

- `stand.ts` — занятие места: доска, connect/register, hello, стук, занятость; схема тула — `standtool.ts`; отказы с рабочим ходом, снятие прежнего места при take и ожидание 429 — `standmoves.ts`; страж стопа на выходе вызова (стоп сессии с начала вызова — места, занятые или привязанные вызовом, снимаются, привязки нет, ответ — слово стопа) и откат перехода при отказе register после connect — `standundo.ts`; полный вызов своего прежнего места — `standagain.ts`; хвост ответа — строка отставания поставки и правила человека из mind (`standtail.ts`, `../shared/mindslice.ts`; не у предварительной посадки харнесса — её ответ модель не читает; #9817).
- `provisional.ts` — предварительное место автопосадки: служебный id и флаг вместе, имя `.root-<12 hex>` (48 случайных бит, остаётся 30 из 48 знаков для основы) против гонки экземпляров; признак живёт в записи держания и сохраняется при возврате и переписывании той же записи той же сессии; явный stand той же сессии в том же графе заменяет только это место без take и снимает признак (#7972, #5164). `seatproof.ts` — этот обслуживающий мост подтверждает семантику полем provisional в held, stand и resume/check; плагин не выводит поддержку старого демона из дисковой записи.
- `board.ts`, `fields.ts`, `standing.ts` — чтение доски и ответов канала, привязка места.
- `hold*.ts`, `resume*.ts`, `separate*.ts` — держание и возврат места, выбор места рядом. Граф места — `@owner/slug` до любого вызова сервера (`seatRealm` в `hearing.ts`, `canonicalRealm` в `realms.ts`; `mind` — как есть); запись прежней сборки с rN или голым слагом `holdcanon.ts` переводит на ключ `@owner/slug` при первом чтении живой (по возрасту, как `readHoldRecord`) записи, прежние ключи остаются в записи (`formerKey`, строка или список): по ним место находит возврат, дверь слушает и на их сокетах, место рядом называется и ими (#8677). Отказ или молчание списка графов негативом не держится — спросится при следующем stand или возврате. Прямые вызовы api вне MCP несут граф `@owner/slug` или числом (`apiRealm` в `realms.ts`; список графов api — `realmindex.ts`). Плагин спрашивает, что за граф rN, методом `realm` (`realmask.ts`, #8191): известное таблицей моста — без сети, иначе один список графов; неразрешённое возвращается как дано.
- `satellite.ts` — место субагента на прогон; `session.ts` — конец сессии; `runend.ts` — конец места с концом агента (сразу по `end`, по окну смерти в демоне — кроме места, которое после конца прогона держал другой мост, его запись держания новее; connect, отвеченный после конца прогона, сокета не открывает и уходит с окном, у спутника — сразу), `deadstop.ts` — снятие канала умершего токеном его мёртвого сокета, исход по месту из `ended[]`, `endword.ts` — то же снятие токеном сразу по слову харнеса (`end`), revoke по имени — только на api без ручки (#9232), `deadseat.ts` — сверка доской для api без этой ручки и запись держания, уходящая только с подтверждённым снятием, `away.ts` — метка объявленной отлучки, при которой место ждёт свою сессию.
- `sessionclose.ts` — закрытие своей сессии MCP: DELETE с её Mcp-Session-Id на выходе сессии моста и при замене сессии, которую сервер ещё держит (`letGo` в `transport.ts`; после 404 — не закрывается), одна попытка с потолком, id и исход — в журнал и `grant.log`; id, выданный сервером, — туда же строкой открытия (#9174); сессию, отложенную окном смерти, демон закрывает и тогда, когда сам уходит внутри окна — по SIGTERM или передачей преемнику (#9306). Проба — `../tests/session-close.test.mjs`.
- `snapshot.ts` — снимок своей области сессии для `status`; `daemon.ts` собирает области в один ответ без открытия сессии.
- `skillwatch.ts`, `skillrefresh.ts` — последнее принятое объявление и единое решение об освежении плоского набора; сериализованная публикация в фоне после ответа на вызов тула, независимо от расхода. Загруженный каталог версии плагина не заменяется соседним.
- `skillcatchup.ts` — догон набора на stand/возврате (#10122): только major/minor и собственный глобальный flat/OpenCode, включая активный XDG-lock внутри HOME. `skillcatchup-manifest.ts` получает полный git-tree SHA текущего выпуска; `skillcatchup-guard.ts` проверяет все имена, источник, реальные пути, симлинки/хардлинки и полный перечень blob-байтов, затем перечитывает ref/hash/version/stamp. `skillcatchup-run.ts` запускает существующий CLI skills 1.7.6 явным списком имён и одним agent, с пределом 20 с и гашением POSIX-группы при сроке/стопе; `skillcatchup-update.ts` держит единственного писателя и ставит обычное освежение метаданных в очередь. Автодогон не поддержан на Windows, для проектного корня, pi и плагинов Claude Code/Codex: только первое слово с командой. Снятое не удаляется. Слова — `../delivery/words/skillcatchup.ts`; нижние пробы — `../tests/skillcatchup*.test.mjs`, API и updater в них подставные.
  `pi-source.ts` — только распознавание источника предупреждения pi: клиент pi, реальный путь стандартной git-установки и её точный origin. Регистрацию пакета у pi не удостоверяет; иных каталогов/форм origin не угадывает. Не расширяет владение flat и допуск автозаписи; неизвестное ведёт к doctor (#10316).
  Блокировка `.agents/.skill-catchup.lock` после запуска add снимается только полным post-read; SIGKILL или любой неподтверждённый исход её сохраняет. Она проверяется до сравнения версий: свежий bridge.VERSION не доказывает полноту набора. Повтор не является восстановлением; сначала оператор подтверждает остановку группы updater и происхождение блокировки. Отказы второго живого писателя, неизвестной блокировки и свежей VERSION при старом SKILL — `../tests/skillcatchup-gate.test.mjs`.
- `status*.ts`, `leave.ts` — занятость, отпускание и возвращение.
- `context-gate.ts` — ограда записи после наблюдённого обвала заполненности OpenCode (#10121); чтение — по `../shared/toolreads.ts`, отдельно от безопасности повтора. Загрузки двери и всего известного списка роли связаны с местом и поколением; неизвестный список требует явного `context_restored` у stand, локально без register. `context-state.ts`/`context-store.ts` — пометка по серверу и месту в своём auth-dir (`*.context-gate.json`, 0600, атомарная запись через `writeOwned`): перезапуск сбрасывает baseline и загрузки, но не известный pending; ошибки чтения/сохранения не разрешают запись. Пробы — `context-gate.test.mjs`, `context-store.test.mjs`, `opencode-context-gate.test.mjs`; порядок живого usage → tool и прокси ими не удостоверены.
  Справка `action="?"` разрешается по объявленному `action` уже полученной схемы: `toolsync.ts` держит её в области сессии; `initialize.ts` берёт однократный снимок серверного кэша при первом initialize и согласует форму счётов (дополнительные мосты OpenCode используют готовую витрину без tools/list); `moment.ts` обновляет по живому/кэшированному списку и перечитыванию после переоткрытия. Уведомление смены поверхности убирает старое разрешение; новый список заменяет его, следующие страницы дополняют. Пробы — `context-schema.test.mjs` и `context gate: help schemas` в `daemon.test.mjs` (две сессии одного настоящего демона).
- `stophold.ts` — остановка снятием места владельцем (чужой 4001, кадр standing_ended): место отпущено и забыто, ни один автоматический путь его не занимает; имя свободно. Кадр standing_ended и приказ останова останавливают лишь место, чей id в них; мост, не знающий id своего места, — лишь адресованные этим id (`to_standing_id`); иначе строка в журнале или отказ приказу (дело №1046).
- `lifeseat.ts` — побудка о живости, адресованная лишь `to_standing_id`, получает имя своего места этого моста (`to_standing`), чтобы текст называл предупреждённое место.
- `stoporder.ts` — приказ останова (кадр `stop` и чтение открытых приказов на hello): тот же стоп, что в `stophold.ts`, и ответ api; `orderack.ts` — ответ по `<origin>/api/me/orders/{id}/ack`, повтор неотвеченного исхода (с подъёма сессии и по hello); `orderflight.ts` — приказы в полёте: конец сессии ждёт их исходов с потолком, неотданное оставляет в журнале; `orderread.ts` — чтение открытых приказов страницами от курсора дома; `orderjournal.ts` — журнал приказов и курсор чтения на диске рядом с грантом; `orderhalt.ts` — подтверждение стопа харнесом (`iskron/halted` клиента с `iskron/halts`).
  `order-client.ts` — вторая локальная фаза текущего полного приказа после подтверждённого interrupt/drop: только свой однозначный Run/standing/realm/handle/runtime, с повторной проверкой поколения и записи; `orca-stop.ts` — show→close→wait exit→show на Orca 1.4.242, с проверкой runtime/handle/incarnation. Потолок archive несётся отдельной фазовой квитанцией и конечной причиной; отсутствие archive не разрешает kill клиента вне своего Run. Старые журналы и произвольные failed-исходы не закрывают клиента; снятие без приказа этот путь не вызывает (#9256).
- `orchestra-runs-delta.ts` — baseline снимков `readRuns` и адресная по-полевая дельта к последнему реестру (#9256); новые соседние строки и нетронутые поля сохраняются, исчезнувшая/заменённая identity старый переход не получает. Неотслеживаемый явный объект `writeRuns` по-прежнему заменяет реестр целиком; повторные записи снимка продолжаются от его собственного последнего записанного вида.
- Явный OpenCode exec (#9967–#9970): `exec-spec.ts` проверяет необязательные `harnesses.opencode.exec.server` (HTTP loopback без credentials) и `modelRefs` (разрешённый непрозрачный token → `{providerID,id,variant?}`). Нет объекта — прежний путь; неправильный объект — отказ, не откат. `exec-preflight.ts` сверяет нужные команды/флаги схемы, положительный local status и платформу/тот же runtime из host name, без пина версии; пользовательское machineName не доказательство локальности. `exec-launch.ts` готовит частную attempt-квитанцию до terminal-create; `exec-attempt-io.ts` держит проверку пути/владельца/0700/0600, no-follow, единственный prepare и fsync; `exec-receipt.ts` — схему/фазы/Run identity. `exec-prepare.ts` внутри окружения Orca вызывает explicit-server API-create/read-back/prompt, затем выдаёт только argv для POSIX exec того же session. Авторизация из демона не переносится. Неизвестный исход удерживает ключ и лимит; квитанция не подтверждает claim/join.
- `exec-client-exit.ts` — show → wait exit → show с теми же handle/runtime/incarnation/path; отсутствие или ошибка не дают exit. `exec-exit.ts` сохраняет наблюдённый выход до обычного stop с причиной `client_exited`; этот наблюдатель сериализован с тактом, но работает и при выключенном флаге подъёма. `exec-raised.ts` читает только raised, с отдельным курсором после сохранения привязок; приглашения не читает, испорченный курсор не обнуляет. Exit без подтверждённого останова не завершает quit; 410 не доказывает подавление побудок. `order-client.ts` не закрывает уже вышедшего своего клиента повторно.
- Разделённые части оркестратора: `orchestra-launcher-types.ts` — схема описания, `orchestra-run-types.ts` — общий договор Run; `orchestra-raise-gates.ts` — прежние caller/offer/limit/cover gates, `orchestra-start.ts` — единый бриф обоих адаптеров, `orchestra-switch.ts` — включение/выключение без изменения согласия, `orchestra-window.ts` — окно, `orchestra-run-ends.ts` — истечение и исход приказа, `orchestra-watch.ts` — дверь и таймер автоматического такта. Для exec истечение/неизвестность не освобождает лимит как успешный quit. Пробы — `../tests/*exec*.test.mjs`; fake Orca/API не удостоверяют живые claim/join и отсутствие поздних побудок.
- `orchestra-resolve.ts` — единый выбор недостающих launcher/harness/model в памяти для сухого и исполняемого такта (#5042); `orchestra-remote.ts` — чтение только hostname через `ssh -G` для SSH remote при поиске проекта Orca, без изменения организации/репозитория (#7517). Неоднозначное или неподтверждённое не выбирается.
- `orchestra-role.ts` — один авторитетный GET карты на рассматриваемый зов, только `adhikarin` допускается к выводу параметров (#5042). `orchestra-only.ts` — одноразовый `step --only UUID/номер --realm граф`: полный снимок читается, но исполняется только один открытый зов, без работы с чужими стопами, уборкой и курсорами; при OFF нужно разовое согласие TTY/`ISKRON_ORCHESTRA=1`, флаг и граница не меняются (#8202).
- `orchestra-status.ts` — состояние машины и именованные остатки своих деревьев, видимые также при OFF; приватные пути и описания не печатает.
- `orchestra-tree.ts`, `orchestra-tree-types.ts` — durable intent и отдельное detached Git-дерево на неизменном OID `origin/main` (#7517); выбранная Orca-копия теперь только источник. `orchestra-tree-check.ts` — Git-факты пути/common-dir/inode/HEAD и чистоты, без исполнения checkout hooks. `orchestra-tree-clean.ts` — удаление только точного своего дерева после наблюдённого выхода клиента и подтверждённого стопа, без force; dirty, новые коммиты, неизвестность и чужая идентичность остаются явно. Обычный launch выбирает объявленный `--surface terminal` (#9969), не создаёт Orca-workspace; `exec-client-exit.ts`, `exec-raised.ts` и `exec-exit.ts` наблюдают также обычные запуски со своим деревом при выключенном автоподъёме.
- `door.ts`, `listen.ts`, `fanout.ts` — локальный сокет и доставка сторожам.
- `graph-retirements.ts` — сверка живой квитанции `ev:latest` со связями вытесненных событий; `graph-retirement-store.ts` — атомарный sidecar `<seenPath>.graph-retirements.json`, схема 1, граница `SEEN_KEEP` (#9904). Один владелец Door пишет sidecar; клиенты независимо дописывают общую `.seen`, которую сверка перечитывает. Тела вопросов не сохраняются: после перезапуска до вручения нужен повтор latest с сервера; после вручения связь позволяет погасить старые события без такого повтора. Отказ хранения удерживает graph в памяти и сообщает ошибку, прочие сообщения проходят.
- `mux*.ts` — общее соединение каналов демона (граф @nks/nks-dev, #8620, #8622, #8623): `muxhold.ts` — держатель канала той же формы, что сокет на место (`holdChannel`), строки занятости и расхода в такт (`tickFor`, им пользуются `statuspost.ts` и `usage.ts`), последняя строка уходящего места (`leavingLine`: такт до отписки, POST — только в откате); `muxroute.ts` — подписки, разводка кадров по каналу, ack, исходы `channel_closed`/`error`; `muxtable.ts` — таблицы подписок; `muxends.ts` — исходы подписки по слову сервера (`error` на подписку, класс `channel_closed`); `muxframe.ts` — к какой подписке кадр; `muxsub.ts` — подписка, окно дедупа, адрес → секрет; `muxlink.ts` — одно соединение на api, откат только на увиденный 404/405, отступ; `muxattempt.ts` — одно открытие; `muxprobe.ts` — ответ апгрейда из канала диагностики undici, а не увиденный — простым GET; `muxlife.ts` — сторож тишины соединения; `muxtick.ts` — пачечный такт; `statusturn.ts` — очередь POST'ов адреса статуса после отката: придержанные строки впереди свежих. Пробы — `../tests/channel-mux*.test.mjs`, фейк — `../tests/fake-mux.mjs`.
- `orchestra.ts`, `orchestra-door.ts`, `orchestra-tact.ts` — оркестратор демона (#7513/#7514): флаг рядом с грантом и граница (названная половина плюс обнаруженная — графы живых мест машины), локальная NDJSON-дверь `on/off/status/step` и один такт чтения invites/raised от курсора; отказ целиком, курсоры не двинуты — и не двинуты после ухода спрашивавшего (#8202, №1317). Слова — `../delivery/words/orchestra.ts`; пробы — `../tests/orchestra.test.mjs`.
- `orchestra-lead.ts` — ведущая половина такта (#7513, #5042; решения дела №4050): лента raised в реестр, полный снимок demands, погашение и подъём; такт идёт сам таймером демона при флаге и согласии машины (демон тогда не уходит по простою). `orchestra-launchers.ts` — описания запускателей человека в mind (`slice:orchestra`, тело — JSON: launcher, host необязателен, adapter, limit, harnesses `{имя: {models}}` — имя и есть `--agent` Orca, checkouts необязательны, callers — необязательный список `@handle` чужих учёток, чьи зовы поднимать, clone/clone_root/allow — необязательное разрешение клона) и учётка ключа демона (`iskron_me` whoami) через `../shared/mcpsession.ts`; `orchestra-raise.ts` — подъём по автору зова (учётка демона или из callers) и attrs зова launcher/harness/model, отказ вслух кодом; `orchestra-orca.ts` — адаптер Orca 1.4.242 (версия и схема до запуска; checkout — ровно один ready-setup `hostId=local` проекта, чей `canonicalKey` или `remoteUrl` равен repository зова, карта описания перекрывает; argv массивом; отказ запуска — кодом Orca `launch_refused_<код>`); `orchestra-orca-answer.ts` — код ошибки из ответа Orca CLI; `orchestra-orca-seen.ts` — ожидание, пока Orca покажет только что созданное дерево (`worktree show`), до запуска в нём (#10598); `orchestra-clone.ts` — клон незнакомого репозитория (#10078): без копии и при `clone` описания — `orca project setup-clone` по https-адресу repository из `allow` в `<clone_root>/<org>/<repo>` (`--project` — id, который Orca выводит из remote, `--host local`, `--destination` — канонический путь родителя), занятую папку не трогает, вывода клона не повторяет; `orchestra-cloning.ts` — сам клон в фоне демона (строка `cloning` реестра, такт не ждёт; неудача помнится по repository до перемены описания — `clone_failed_before`; git идёт в рантайме Orca — таймаут гасит только клиента); `orchestra-runs.ts` — реестр запусков и строк клона; `orchestra-quench.ts` — погашение своих запусков по пустому составу приказом `composition_empty` после перечитывания ленты; `orchestra-flag.ts` — флаг рядом с грантом и согласие машины: `ISKRON_ORCHESTRA=1` у демона либо `on`, набранная в терминале (лежит во флаге, `off` снимает); `orchestra-describe.ts` — `on --launcher`: описание запускателя пишется в mind ключом демона, только если описания с этим launcher там нет (любой host, даже битого), — `context` к единственному холону, держащему карточки `slice:agents`, иначе в корень; launcher длиннее 64 — отказ; `orchestra-plan.ts` — сухой такт (`step --dry-run`): те же снимок, описания и реестр, судит зовы как подъём и ничего не делает; `orchestra-foreign.ts` — останов по требованию: чужой приказ месту нашего запуска (GET /me/orders всех состояний от курсора `orchestra-orders.json`) переводит строку в stopping или ended — слот и терминал освобождаются, как после своего приказа. Пробы — `../tests/orchestra-raise.test.mjs`, подставной `orca` — `../tests/fake-orca.mjs`.
- `orchestra-demands.ts`, `demand-rows.ts` — явное `demands` той же двери: полный список invites по каждому названному графу границы и все страницы открытых stop своей учётки; структура без секретов, `complete/errors`, без курсоров и побочных действий (#9957/#9958). Флаг автоматики не включает. Пробы — `../tests/orchestra-demands.test.mjs`.
- `pulse.ts` — кадр живости сокета канала (`pulse`): свои cycle_at и pending, слово харнеса (`iskron/pulse`) о ходе — state, turn_at, read_at, act_at (моменты только вперёд; act_at из cycle_at не выводится); `pending.ts` — его счёт pending по дверям; `work.ts` — последний вызов тула агентом. `../tests/pulse-latest.test.mjs` — управляемое время на пути RPC → держатель → такт: последний снимок к ближайшему такту и 30-секундный интервал при откате на старый сокет (#8743).
